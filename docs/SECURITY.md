# Security

Treat the gateway as potentially compromised. It can consume allowed GPU services and see the data sent through them. It must not select arbitrary LAN hosts, reach administration paths, supply upstream credentials, run commands or change configuration. Local route profiles, strict path/header checks, body/concurrency/rate/idle limits and restricted dialers form the application boundary. systemd adds an unprivileged account, empty capabilities, filesystem restrictions and default-deny IP egress. The optional health listener is off by default and must bind localhost.

Ordinary TLS verification and a nonce/time-bound Ed25519 signature are both required. Obtain server keys through an independently authenticated channel. The signature proves that a holder of the pinned key signed those handshake fields; it is not bound to the TLS connection and does not encrypt the subsequent session. The bearer token is sent in the upgrade before signature verification. An attacker with a certificate trusted by this host, including a hostile TLS inspection proxy, can relay the upgrade to the real gateway, return its valid signature, capture the token and then observe or inject locally allowed requests. Pinning does not prevent that relay. Treat trusted CAs and proxies as part of the security boundary; end-to-end protection through an untrusted inspection proxy would require an additional authenticated encryption design, which is not implemented.

For server-key rotation, independently verify and install both old/new public keys, reload locally, switch the server, then remove the old key. Never accept a key learned only from the connection it is supposed to verify. No production public key is supplied.

The local token is a bearer credential. Store token and file-backed upstream secrets as root-owned 0600/0640 files with only the service group permitted to read them. Configuration is local; the cloud cannot push updates. Updates are explicitly installed by the operator. Verify signed checksums and review SBOM/vulnerability results before upgrading.

Audit JSON lines record timestamp, session, route, method, path, status, input/output byte counts, duration, upstream and request ID, plus the gateway model name and upstream model id when a route's model alias rewrote the request. They intentionally omit prompts, outputs and secret headers. Review unexpected denied paths, excessive usage and reconnect/signature failures through the service journal and audit file. Request metadata remains sensitive; restrict and rotate logs.

The process-level policy and container sandbox do not replace an OS egress boundary. IP filtering must be tested on the deployment kernel; systemd IP restrictions are IP-based, while the application also limits ports. Compromise of an allowlisted upstream service and malicious content generated by a model require separate controls. The standalone test gateway is a loopback development harness, not production tenancy, token revocation or metering infrastructure.

Report vulnerabilities through [GitHub private reporting](https://github.com/eidonix-ai/eidonix-connector/security/advisories/new) when the repository owner has enabled it. Enablement has not been verified and is required before public announcement. If that page is unavailable, ask a maintainer for a private contact without posting exploit details, tokens, configurations or customer data publicly. No dedicated security mailbox has been supplied.

Model aliases are the only request-body rewrite. On routes that define them, the connector parses just the top-level JSON object (or multipart form fields) to replace the `model` value, and rejects malformed bodies and duplicate `model` keys rather than forwarding a body the connector and upstream could read differently. Aliases translate names; they do not restrict which models the gateway may request.

Allowed request bodies can still contain remote resources such as `image_url`, document URLs or converter directives. The connector does not understand every upstream body schema and cannot prevent an allowed model/converter server from fetching those URLs. Sandbox and restrict egress on the upstream servers themselves, and disable remote fetch functionality where possible. Local connector method/path restrictions alone do not prevent upstream-induced SSRF.

Public contributions must use synthetic test data and documentation addresses. Keep customer configurations, captured traffic, internal rollout plans and credentials out of commits. Local environment files and key material are ignored; CI scans Git content for secrets. Secret scanning complements manual review of customer and infrastructure information.


## Object storage trust boundaries

The gateway can request only put, get, head, list, delete and same-prefix copy on one locally configured bucket/prefix. It cannot supply endpoint settings, credentials or encryption keys, access the reserved local probe area, administer buckets or mint presigned URLs. Key checks, concurrency limits, size limits, operation rates, an optional read budget and local audit bound access. They do not provide per-user object authorization: the production gateway must authorize each user and object separately.

A compromised gateway can read every permitted non-client-encrypted object as plaintext through `get`, and overwrite or delete permitted objects. Storage SSE-C does not prevent that: the connector supplies the key to the storage backend and returns decrypted bytes to the gateway. Protecting content from a compromised gateway requires client-side encryption performed before upload, with keys unavailable to both gateway and connector. Client-encrypted vault objects remain ciphertext while passing through them; server-side encryption does not add or remove that property.

SSE-C sends the customer key to the live storage service in each relevant request, over verified HTTPS. An honest service uses it for encryption/decryption without retaining it; the mode helps protect offline ciphertext or stolen storage credentials that lack the key. A malicious live storage server or administrator able to intercept those requests can capture the key and plaintext. SSE-C does not protect against that adversary or a compromised connector host. SSE-S3 and SSE-KMS also do not hide plaintext from authorized storage reads. The key-handling and HTTPS requirements are described in [AWS SSE-C guidance](https://docs.aws.amazon.com/AmazonS3/latest/userguide/ServerSideEncryptionCustomerKeys.html).

Storage audit entries include operation, a keyed HMAC of the relative key, byte size, status, checksum-verification outcome and duration. They omit raw keys and contents; local checks, cleanup and probes use `origin: local`. Failed or interrupted reads can still consume the read-byte budget because their announced length is reserved up front. Limits are per route runtime, not a fleet-wide budget. Monitor aggregate usage and protect audit files on each host. `report_location` is false by default; enabling it exposes bucket and prefix names to the gateway for display.

Incomplete uploads remain invisible until framing, byte counts, SHA-256 and clean EOF verify and backend commit succeeds. A failed abort or process crash can leave invisible multipart data; local sweeps and an operator-installed lifecycle rule provide cleanup. The six-hour upload maximum and 24-hour cleanup minimum require synchronized clocks and the same policy on every instance sharing a prefix. See [installation](INSTALL.md) for the restricted credential template and explicit write-probe behavior.

A compromised storage backend can return malicious metadata or content. Wire/body/metadata bounds limit memory exposure, but downloaded content still needs normal application handling. Gotenberg conversions and model APIs may themselves fetch resources from request bodies: disable Gotenberg download-from and isolate converter/model egress independently of the connector (see [installation](INSTALL.md)).
